## Choose what to transfer

Separate three things: the design problem a reference tries to solve, its proposed remedy, and the evidence that the remedy works here. A conflicting remedy can teach a useful principle without becoming a default.

1. Protect scientific truth, source content and the task's authorized scope first.
2. Retain the user's explicit style choices and the accepted project reference. Do not let an external package silently redefine either.
3. Add compatible methods where they solve an observed problem. Use conditional alternatives for conflicts; show them only when they would improve the current task or a meaningful tradeoff needs a decision.
4. Treat journal-like presets as design examples, not official requirements. Verify a specific journal's current instructions before claiming compliance. Distinguish an established manuscript convention from a requirement.
5. Keep a short task-local rationale: observed defect, relevant reference idea, proposed adaptation, protected properties, and actual result. Do not insert private task evidence into this reusable module.

## Improve the first arrangement

Before choosing boxes, privately map each panel to its scientific role, the source-supported question it addresses, its relationship to other panels, and its smallest necessary readable details. Infer these from supplied evidence; ask only when unresolved meaning changes the layout. A quick appearance-only fix does not need a new scientific narrative or questionnaire.

Compare a small number of sensible arrangements rather than filling a fixed template:

- **Peer comparison:** give genuinely comparable measurements similar readable scale and adjacent placement. Preserve any existing differing axis ranges; a shared visual row does not authorize changing data scales.
- **Orientation followed by evidence:** lead with a device overview or process schematic when it is needed to understand later measurements. Keep an overview useful rather than automatically making it the largest object.
- **Result with supporting evidence:** make a key result easier to find when the source/user establishes its importance. Allocate extra room where data density, uncertainty marks or long labels require it, not just where a panel looks attractive.
- **Image plus quantification:** keep a measurement image, scale bar, ROI and its verified quantification close enough to associate, without making image and plot containers artificially identical.

Use reading order, adjacency, whitespace and the existing color semantics to guide attention. Prefer purposeful visual hierarchy over a mandatory dominant panel or a fixed area multiplier. A source showing several equal comparisons may need no hero at all. A negative or null result can be the central finding.

Check whether panels repeat the same question, but do not automatically delete, merge, replace or derive a new statistic. Repetition may establish reproducibility, a control, an alternative representation or a necessary comparison. Flag only material redundancy; preserve the complete source set unless a subset is confirmed. For light refinement, keep the accepted composition and use this reasoning to improve spacing, not to redesign the story.

Judge candidate arrangements in this order: intact scientific content and relationships; readable final-size details; clear question/sequence; coherent frame-and-ink alignment; balanced internal/outer whitespace. Do not use a numerical aesthetic score to trade away any failed scientific or readability gate. Reuse the existing quick HTML workflow; this module adds reasoning, not a new automatic layout engine.

## Reserve space for semantic accessories

Colorbars, legends and insets need explicit space alongside plots, rather than whatever space an automatic grid happens to leave.

1. Identify each accessory's owner and complete visible extent, including title, units, tick labels, legend swatches and annotation runs. Include these extents in the clearance inventory before distributing panel gutters.
2. Allocate a plot region and an accessory region separately where useful. Compare actual plot frames across peer panels, not their unequal outer boxes containing titles or colorbars. Keep the surrounding optical grid coherent while allowing intentional unequal image/plot proportions.
3. Keep a colorbar near the panel or verified panel group it explains. Share one only if variable, units, normalization, numeric limits, transforms and category mapping are genuinely identical, and the change is within the confirmed plan. Never alter a scale to make sharing possible. Different scales should remain visibly distinguishable.
4. Prefer a compact legend in verified empty space when it remains readable and cannot cover evidence. Consider an outer gutter when no safe internal position exists. Check every curve, marker, uncertainty band and inset against the actual final legend extent; a legend being inside the panel proves no such clearance.
5. Preserve exact labels and scientific runs. Reclaim whitespace or translate the relevant group before shrinking text. Wrapping, abbreviating, hiding a label or moving information into a caption is not automatically allowed because a reference recommends it; propose the exact content change when required.
6. If automatic packing gives an uneven visual grid, use explicit measured geometry through the selected supported route. Do not treat an automatic layout function's success or an imported bounding box as evidence of true frame, ink or baseline alignment.

Audit repeated scientific identities across the whole figure set, not just within one panel: colors, marker/dash meaning, units, typography roles, uncertainty encodings and panel-letter treatment. An inconsistency is a finding to resolve, not permission for global recoloring or rewriting. A rendering-metadata change does not establish that the actual image changed.

## Learn from conflicting prescriptions

Use the following distinctions rather than importing hard rules wholesale:

| External prescription | Useful design reason | Adaptation for this workflow |
| --- | --- | --- |
| Always use a hero panel, larger and more saturated | Make the reader's entry point obvious | Let supported scientific importance and density set emphasis; preserve peer equality and existing scientific colors when appropriate. No compulsory ratio or recoloring. |
| Always put data before schematics | Avoid letting an unsupported model appear to prove a result | Distinguish an orienting device/method overview from a conclusion schematic. Either order may be correct; preserve the accepted narrative and evidence boundary. |
| Remove repeated panels | Reduce cognitive burden | Review redundancy, but retain controls, replication and useful alternate views. Obtain confirmation before omitting or merging supplied content. |
| Use fixed 89/183 mm widths and fixed font/line values | Design for the final reading size | Use the actual requested medium and verified journal size. Treat numeric presets as starting examples; measure final glyphs and strokes after the full transform chain. Do not change the user's canvas or smaller/larger role hierarchy merely to pass a preset. |
| Remove top/right spines and grids; use outward ticks | Reduce decoration and data interference | Inspect whether a frame, grid, secondary axis or tick direction carries meaning or matches the accepted style. Keep it by default; propose a narrowly scoped appearance change if useful. Never remove scientific axes or ticks under layout approval. |
| Ban every built-in palette or impose a journal-branded palette | Encourage deliberate, accessible color choices | Judge distinguishability, ordered scales and semantic consistency, not whether a palette is a default. Preserve current colors; offer tested alternatives with explicit identity-to-color mapping when recoloring is requested. |
| Always place legends outside; share scales/colorbars | Recover data area and simplify repeated explanations | Choose actual empty space and stable associations. Sharing requires scientifically identical mappings and authorization; external placement must not compress the plot or detach its explanation. |
| Shorten/hide labels or remove italic text to fix crowding | Reduce visual overload | Preserve exact scientific text, labels and italics with semantic meaning. Prefer translation and whitespace recovery; confirm substantive label changes rather than silently dropping detail. |
| Uniform peer boxes and minimal non-data marks | Produce a quiet, regular publication composition | Align true semantic peers and preserve meaningful proportions. Do not misread decluttering as permission to remove the workflow's visible, independent guide group. Use the clean companion for aesthetics review, never as a replacement for the required guided final. |
| Deliver PDF plus PNG for every request | Preserve editable line art and provide an easy preview | Deliver the requested format and verified edit layer. A vector container with embedded bitmaps is not wholly vector or natively editable. Offer extra formats only when useful and allowed. |

A null difference, weak correlation, flat response, overlapping groups or large uncertainty is not a visual-quality failure. Do not borrow significance, correlation, effect-size, variance or pixel-density thresholds as acceptance tests for real scientific data. Use sparse or empty-looking output only as a prompt to verify bindings, clipping, missingness and rendering against the actual source. Never modify observations, simulation parameters, axis limits or normalization to manufacture an attractive signal. Separately requested simulation changes must follow their own scientific scope, not a cosmetic QA repair.

## Keep audit evidence honest

Separate four review layers: source/allowed changes; explicit layout and text measurements; actual full-size and detail renders; application reopen/save/refresh. The established quality specification already provides the acceptance gates; do not replace them with a new checklist merely to get a green result.

The reviewed Scientific Figure Skills layout/text auditors primarily consume supplied metadata and boxes. Its text-repair script can hide labels, abbreviate a colorbar title, rotate tick text, or mark a collision check complete in metadata. Those operations do not prove a collision was measured or a renderer updated. Do not import that behavior, promote a checked flag into evidence, or claim the upstream audit repaired an existing PPT/Origin figure. Every changed visual property still needs a supported writer and a fresh inspected result.

The reviewed Academic Figure Skill mixes useful render review with rigid style checks and signal-strength checks. Its typography and checklist even disagree on a baseline font value. Treat these as reasons to examine the rendered artifact and scientific source, not to force the existing figure through its validator. No external test suite was executed in this review.

When export is requested, verify the actual canvas, dimensions, crop, file existence and pixel/vector content. A tight crop can change the physical page or relative scale. Confirm fonts/glyphs in the output; a nominal font name or vector extension is insufficient. Keep the existing same-canvas comparison for revisions and the requested output boundary.

## Treat OriginLab-MCP as a candidate engine

The reviewed Yike-Ye project is an Origin execution bridge, not an aesthetic authority. Its documented host/VM route runs the MCP server inside Windows, reaches Origin over a loopback socket, and carries MCP traffic over SSH from the host. It advertises worksheet operations, graph/layer creation, arrangement, axes/legend changes, selected LabTalk options and PNG export. These claims do not establish availability in the current environment or native PPT/OLE integration.

Transfer its most useful verification lesson: distinguish a requested value, a stored readback, an actual exported appearance, and a persisted native change. A successful LabTalk return can be a no-op; a readback can match while group styling overrides the picture. Discover real graph/layer/plot identity and group membership, verify the exported file exists, inspect the render, compare protected science, and separately verify native reopening and PPT refresh when those are part of the requested result.

Retain these specific limits from the reviewed source:

- The project claims Origin 2024 and a five-panel example were tested by its author; this workflow did not repeat those tests. A documented option catalogue is not a test of every option. Its README reports visual checks for only 16 of 213 documented options.
- Built-in legend placement checks containment, not data occlusion. Log axes and group-member styling have specific limitations. Only the implemented operations for the current version count.
- The dedicated graph export path writes PNG with overwrite enabled and returns a requested path, not file-existence proof. Use unique authorized output names and verify the actual file. It is not by itself a PDF/SVG export, a project-save API or a PPT reinsertion/refresh workflow.
- Arbitrary LabTalk is a broad execution surface. A failed multi-statement call may have already executed a prefix; inspect state before any retry. Prefer narrow reviewed operations over a general command escape hatch.
- Source checks restrict bridge binding to loopback and use a token/session pair. That does not make it a least-privilege, task-directory-restricted bridge. The Windows token protection relies on the user's temporary-directory permissions. Review the actual account, filesystem and command scope before use.
- SSH setup, key creation/configuration, service startup, permissions or persistent MCP access are separate security-sensitive actions. Do not install, enable, connect, restart or expand access merely to evaluate the project. Existing finite-session authorization must not silently become a persistent SSH/MCP setup.
- The bridge uses Origin's UI thread; modal dialogs can stop replies and a handshake file can be stale. Do not interpret a listed bridge as a responsive one or retry an uncertain write blindly. The README's corrected OPX installation flow and an older remote-setup paragraph disagree, so recheck current installation instructions before any later authorized setup.

Use `refinement-routes.md` and `bounded-native-methods.md` for the actual route and permission boundary. No upstream code, runtime, launcher, credentials or installation command is added by this module.
