# Reuse verified toolkits without losing their scope

An earlier conversation's verification is useful evidence. Do not discard a real
native application result merely because the current machine is unavailable, and
do not present a repeat of an old fixed-byte result as a new capability.

## Four separate acceptance questions

1. **Is the supplied artifact intact?** Check archive integrity, path safety,
   manifests, dependencies and provenance before execution. Keep private samples,
   source fingerprints, offsets, logs and machine/session details out of reusable
   skills and public repositories. Owning a copy is not a software license.
2. **Can the operation be reproduced now?** Rerun supported pure-file operations
   on independent copies. Compare output bytes with the exact recorded candidate;
   a different source or changed parameter is a new case. Exercise stale input,
   unsupported operations and existing-output refusal, not only happy paths.
3. **What did the earlier application actually verify?** Distinguish exact
   candidate cold-load/render evidence from an API-modified project later saved
   by the application. Check that report identities and image bytes agree. A
   completion marker, source name or similar-looking graph is insufficient.
4. **Does that evidence apply to this task?** Resolve the requested source/version
   again. Do not swap in an old attachment for a named current desktop file.
   Source-specific patches must refuse a new source rather than changing the
   expected hash. Successful regeneration does not prove composability, arbitrary
   parameters, PPT reinsertion, cache refresh or application save/reopen.

## Integration order

- Retain known-good exact examples as private regression cases with explicit
  source identity, supported operations and provenance. Reuse the evidence; do
  not rerun a full application workflow for every byte-identical regeneration.
- Integrate reusable pure-file checks separately from native application workers.
  A bridge's historical session is not currently connected and does not grant
  permission to restart listeners, install software or expand access.
- Test native PPT editing independently of native Origin editing. In PPT, page
  numbers refer to presentation relationship order, not `slideN.xml` filenames.
  Text can inherit font attributes; writing only already-present run properties
  may silently do nothing. Verify actual intended nodes and preserve scientific
  text, scripts and all unrelated object/member content.
- Use an independently reviewed implementation and fresh synthetic regressions
  before promoting a repaired module. A package's own passing tests do not rule
  out missing cases. Keep source hash/old-value guards and the complete permitted
  change comparison around any imported module.
- Apply the same final-size aesthetics regardless of execution engine. Native
  font points and layer coordinates are not directly equivalent to rendered PPT
  typography or physical millimetres. Never apply a fixed sample's absolute
  typography as a universal default.

## Status language

Report **reproduced locally**, **previous exact-candidate application evidence**,
**not applicable to this source**, **failed**, and **not run in the application**
separately. A rejected unfamiliar source can be a correctly functioning safety
check, not a broken tool. A known clipping experiment remains an experiment,
even when its bytes and application load are reproducible.
